# Starting9 V3.5 Automation Core Design

> Status: design only. This document does not authorize implementation, deployment, migration, manual SQL, repair, job submission, or production operation.

## 1. Executive summary

V3.5 redesigns the automation core only. A full rebuild is unnecessary and out of scope. Public UI/API, prediction save, the existing 99-point scoring rules, ranking, roster source of truth, lineup artifact health, cancellation behavior, admin-v3 foundations, and existing tests remain.

The target is planner, orchestrator, executor, workflow/effective state, due and recovery decisions, artifact health, cancellation priority, and server-side diagnostics. The goal is reliable automatic operation and evidence-based diagnosis when persisted state, jobs, upstream data, and artifacts disagree.

Migration starts with shadow and canary operation. Every phase is feature-flagged and reversible.

## 2. Current V3 problem statement

- Job lifecycle and artifact health are separate models; `completed` is not proof of a usable result.
- `workflowState` can become stale and block later stages even when artifacts show progress.
- Recovery is distributed by stage, so missing due jobs, terminal failures, expired `retry_wait`, and completed-without-artifact cases have inconsistent rules.
- Cancellation/exclusion is not yet one universal priority contract.
- Admin diagnostics are assembled after the fact and can mix page, job, artifact, and cron timestamps.
- Multi-slot stages, especially `roster_fetch`, make “latest job” an unsafe substitute for selected-slot evaluation.
- Public official-live data can be valid while a formal job or canonical snapshot is missing; these facts must be separated.

The current code already contains useful roster verification, lineup artifact checks, recovery, cancellation, and structured audit pieces. V3.5 unifies their contracts instead of deleting them.

## 3. Design principles

1. `workflowState` is a checkpoint/audit fact, not the sole truth.
2. Derive `effectiveState` from game status, jobs, artifacts, schedule, prerequisites, and current time.
3. Completion means `job completed + artifact valid + state reconciled`.
4. `cancelled`, `postponed`, and `excluded` have priority over ordinary stages.
5. Due, open, retry, terminal failure, recovery, and missing-job evaluation is common to every stage.
6. Diagnostics are normalized on the server; admin-v3 does not infer business state from raw rows.
7. Public APIs, scoring/ranking behavior, roster semantics, and the MAX99/99-point rules remain compatible.
8. New metadata is additive and nullable so old readers can ignore it.
9. Evidence is append-only and idempotent; existing jobs and artifacts are never deleted.
10. Planner, claim, and executor flags are independently controllable.

## 4. Effective state model

### 4.1 Precedence

```text
cancelled / postponed / excluded
        ↓
published artifact
        ↓
ranking artifact
        ↓
scoring artifact
        ↓
finalized lineup artifact
        ↓
lineup candidate/canonical health
        ↓
prediction close completion
        ↓
roster health
        ↓
probable starter / NPB identity
        ↓
schedule registered
        ↓
scheduled
```

This is precedence, not an unconditional progression. A cancelled game remains cancelled even if stale publication data exists. A published state requires a valid publication marker and artifact evidence.

Persisted `workflowState` remains for checkpointing and audit. A disagreement with derived `effectiveState` produces `STATE_RECONCILE_REQUIRED`; read-only evaluation must not silently mutate it.

### 4.2 Common stage contract

Every stage follows:

```text
evaluatePrerequisite → evaluateDue → planJob → claimJob → execute
→ validateArtifact → persistCompletion → reconcileState → emitDiagnostics
```

The stage registry covers `schedule_registration`, `probable_starter`, `roster_fetch`, `prediction_close`, `npb_game_identify`, `lineup_fetch`, `lineup_finalize`, `scoring`, `ranking_reflect`, `publish`, and `cancel_exclude`.

Per-stage differences are limited to due schedule, prerequisites, executor, artifact validator, and retry policy. A registry entry must also define cancellation behavior, diagnostic labels, and identity requirements.

### 4.3 Common classifications and actions

```text
NOT_DUE
DUE
OPEN_JOB_EXISTS
COMPLETED_ARTIFACT_READY
COMPLETED_ARTIFACT_MISSING
MISSING_JOB
RETRY_WAIT_DUE
RETRY_WAIT_NOT_DUE
TERMINAL_FAILED
TERMINAL_CANCELLED
BLOCKED_BY_PREREQUISITE
BLOCKED_BY_CANCELLED
BLOCKED_BY_EXTERNAL_FETCH_DISABLED
BLOCKED_BY_MANUAL_ATTENTION
RECOVERY_PLANNED
READY_TO_CLAIM
```

| Classification | Action |
| --- | --- |
| `NOT_DUE`, `RETRY_WAIT_NOT_DUE` | wait |
| `DUE`, `MISSING_JOB`, `READY_TO_CLAIM` | plan/claim the selected slot |
| `OPEN_JOB_EXISTS` | wait or claim the existing job atomically |
| `COMPLETED_ARTIFACT_READY` | no-op |
| `COMPLETED_ARTIFACT_MISSING`, `TERMINAL_FAILED`, expired `RETRY_WAIT` | bounded recovery or `ATTENTION` |
| `TERMINAL_CANCELLED`, `BLOCKED_BY_CANCELLED` | no-op/cancel open work |
| prerequisite/external/manual blockers | wait and surface the blocker |
| `RECOVERY_PLANNED` | do not create a duplicate |

Each result includes selected slot, evidence, blocker, and `nextSafeAction`.

## 5. Recovery contract

### 5.1 Metadata and reasons

Every recovery records:

```text
recoveryOfJobId
recoveryReason
recoveryGeneration
requestedAt
requestedBy
source
originalScheduledSlotAt
recoveryScheduledSlotAt
```

Allowed initial reasons are:

```text
MISSING_DUE_JOB
TERMINAL_FAILED
RETRY_WAIT_EXPIRED
MAX_ATTEMPTS_REACHED
COMPLETED_ARTIFACT_MISSING
STATE_RECONCILE_REQUIRED
SOURCE_MISMATCH
SNAPSHOT_MISSING
STALE_ARTIFACT
```

### 5.2 Slot and uniqueness rules

Recovery never mutates the original slot or destroys its history. The base uniqueness rule remains `(internalGameId, jobType, scheduledSlotAt)`. A logical recovery key must also include original slot, reason, and generation:

```text
internalGameId + jobType + originalScheduledSlotAt + recoveryReason + recoveryGeneration
```

The repository operation must be idempotent so concurrent cron runs return “already planned.” `recoveryGeneration` is monotonic and bounded. At the bound, return `MAX_ATTEMPTS_REACHED` and require attention. No recovery is created after cancellation/exclusion.

## 6. Unified artifact health

Every stage returns:

```text
available, valid, fresh, source, capturedAt, fingerprint,
verificationStatus, internalGameId, rowCount, reason,
blockingReason, nextSafeAction
```

Validators cover probable starter rows, roster snapshot/official-live verification, prediction-close marker, lineup candidate/canonical/finalized artifacts, scoring result, ranking reflection, and publication marker. `available`, `valid`, and `fresh` remain distinct. Identity, row shape/count, source, fingerprint, and revision references are checked.

## 7. Roster-fetch design

`roster_fetch` is evaluated per slot, never by selecting only the latest job.

Public `latest_official_live / verified` may be usable when source, identity, and verification are valid. That does not prove a formal V3 job completed or that a canonical snapshot exists. The formal policy must explicitly decide whether official-live verification is itself a formal artifact or whether a canonical snapshot is always required.

The health model distinguishes official-live preference, canonical/verified snapshot presence, fingerprint, capture time, `ROSTER_SNAPSHOT_MISSING`, multiple slots, stale snapshot, source mismatch, terminal failure, and official-live-without-formal-job.

Expected behavior:

- Public data may use valid official-live data.
- Formal automation exposes snapshot/verification as an artifact.
- Missing snapshot exposes a reason and safe next action.
- An overdue missing slot becomes `MISSING_JOB` and may receive bounded recovery.
- Failed/retry terminal states may recover only for eligible, non-cancelled games.
- A baseline or stale snapshot is never fresh merely because it exists.

## 8. Prediction close and lineup gates

`prediction_close` separately evaluates deadline, job, completion marker, and persisted state. Deadline passed with no marker is recovery-eligible. Completed job with stale state is `STATE_RECONCILE_REQUIRED`. `lineup_fetch` receives a blocker and safe next action instead of bypassing the gate.

Lineup evaluation keeps `LINEUP_NOT_YET_AVAILABLE`, `nextRetryAt`, `GAME_CANCELLED`, `NPB_IDENTITY_UNRESOLVED`, candidate, canonical, finalized, official response code, internal ID mismatch, invalid row count, and unresolved player identity separate.

Official absence means retry; official cancellation means cancel/exclude; missing candidate is not completion; canonical is required before finalization; finalized lineup is required before scoring.

## 9. Downstream artifacts

```text
finalized lineup → scoring artifact → ranking reflection artifact → publication marker
```

The existing 99-point scoring behavior is unchanged. A valid zero-prediction no-op remains a valid scoring result under the existing revision contract. `rankingExcluded` is an eligibility fact, not a ranking-job failure. Cancelled/excluded games preserve predictions and skip scoring/ranking/publish as required.

## 10. Cancellation priority

All stages use:

```text
if game cancelled/excluded:
  no new job
  do not claim open job
  cancel/skip pending job
  preserve predictions
  skip scoring/ranking/publish
  rankingExcluded = true
  public cancelled display
```

Official cancellation records source response and observation time. Manual cancellation keeps existing authentication, confirmation, and audit requirements. `postponed`, `cancelled`, and `excluded` remain distinct: postponed may be rescheduled, cancelled is official cancellation, and excluded is an explicit operational/eligibility decision.

## 11. Admin-v3 diagnostics model

The server returns a normalized model; admin-v3 renders it without inferring state from raw arrays.

### 11.1 Explicit times

```text
apiObservedAt
pageRefreshedAt
latestJobUpdatedAt
latestArtifactCapturedAt
latestCronRunAt
latestStateReconciledAt
```

“Last updated” must identify its source, such as `Latest job update` or `Latest artifact capture`. `pageRefreshedAt` is presentation metadata, not automation evidence.

### 11.2 Per-stage response

```text
stageName
dueAt
selectedSlot
healthStatus
jobLifecycle
recovery
artifactHealth
blockingReason
nextSafeAction
attentionLevel
lastError
```

`jobLifecycle` includes ID, status, lifecycle timestamps, attempts, retry time, and recovery metadata. Internal paths and raw exceptions are not public data; admin responses use bounded reason codes and safe details.

### 11.3 Cron observability

```text
cronRunId, runAt, plannerReached, gamesConsidered, jobsPlanned,
jobsSkipped, skipReasons, insertAttempted, insertSucceeded,
claimAttempted, claimSucceeded, executorStarted, executorCompleted,
executorFailed, durationMs
```

The model distinguishes planner-not-reached, no eligible game, existing-job skip, uniqueness rejection, claim failure, and executor failure.

## 12. Persistence and schema evolution

This design does not approve a schema change. If job metadata cannot safely live in existing audit details, add nullable columns or an append-only table through normal migrations. Deploy tolerant readers before writers, keep old rows, and never rely on manual SQL or destructive backfills.

Possible placement is nullable job metadata for queryability plus immutable audit details for history. The choice is an open decision. New uniqueness must be measured against existing duplicates before rollout.

## 13. Coexistence, migration, and rollback

```text
Phase 0: clean baseline / production evidence
Phase 1: derive-only evaluator
Phase 2: shadow planner
Phase 3: roster_fetch canary
Phase 4: prediction_close + lineup canary
Phase 5: scoring/ranking/publish canary
Phase 6: old planner retirement
```

Phase 0 uses a clean `origin/main` worktree and read-only evidence. Phase 1 adds pure evaluation only. Phase 2 records shadow decisions without writes. Phases 3–5 enable small allowlists one stage group at a time. Phase 6 requires an observation window, rollback rehearsal, and zero P1/P2 discrepancies.

Rollback is a feature flag, not reset or deletion:

- stop V3.5 planner insertion;
- route planning back to old V3;
- identify V3.5 jobs with nullable source/recovery metadata;
- let old readers ignore unknown metadata;
- preserve all jobs, artifacts, state, and audit records;
- prevent dual claiming through controlled planner flags and existing leases;
- keep admin diagnostics able to show V3.5 evidence after rollback;
- never automatically retract already-published valid data.

## 14. Implementation work packages

Implementation remains deferred and should be split into:

1. stage health evaluator — pure, derive-only; risk is precedence errors; test every classification;
2. artifact health adapter — additive reader; risk is treating available as valid; test source/freshness/identity;
3. admin diagnostics normalization — read-only API/UI; risk is timestamp and data leakage; test response contract;
4. shadow planner — flagged observation; risk is slot/duplicate divergence; test parity and idempotence;
5. roster-fetch canary — allowlisted; risk is snapshot policy and stale baseline;
6. prediction-close canary — allowlisted; risk is deadline/gate bypass;
7. lineup fetch/finalize canary — allowlisted; risk is partial official data;
8. scoring/ranking/publish canary — allowlisted; risk is public regression and double reflection;
9. old planner retirement — controlled release; risk is rollback and legacy assumptions.

Each package requires explicit risk acceptance, deterministic fixtures, and a deployment type before code work begins.

## 15. Test plan

Minimum coverage:

- due job missing;
- terminal failed recovery;
- expired `retry_wait`;
- completed artifact missing;
- stale state reconciliation;
- cancellation priority;
- NPB fetch disabled;
- missing/stale/mismatched roster snapshot;
- official-live verified and official-live-without-formal-job;
- lineup not yet available and official cancellation;
- candidate/canonical/finalized and scoring prerequisites;
- ranking excluded and Daily Best Nine/Perfect eligibility;
- duplicate cron, duplicate job prevention, and bounded recovery generation;
- internal ID/row count/player identity validation;
- admin diagnostics and timestamp correctness;
- public API compatibility;
- unchanged 99-point scoring and zero-prediction no-op;
- rollback flag, coexistence, and nullable metadata compatibility.

Fixtures must be deterministic across JST/UTC and include multiple roster slots. Assertions must cover both classification and `nextSafeAction`.

## 16. Open decisions

Before implementation, owners must decide:

- recovery metadata in nullable job columns, audit, or both;
- cron observability in D1, structured logs, or split storage;
- whether verified official-live is a formal artifact;
- future ranking eligibility wording;
- postponed/cancelled/excluded state boundaries;
- canary selection and rotation;
- per-stage recovery generation/time limits;
- stable fingerprint/source version policy;
- observation window and release criteria;
- admin read-only versus authenticated job-request boundaries.

## 17. Self-review

### P1 release blockers

- cancellation can create/claim new work;
- completed jobs can publish without valid artifacts;
- concurrent planners can duplicate claims;
- recovery loops are unbounded;
- rollback can delete or corrupt data.

### P2 material risks

- overdue slots can disappear without `MISSING_JOB`;
- stale state can block valid artifacts;
- “last updated” can misrepresent evidence;
- official-live/formal snapshot semantics can diverge;
- old readers can fail on metadata.

### P3 quality risks

- multi-slot diagnostics may be difficult to read;
- reason codes may need operator-friendly copy;
- cron summaries may need additional cardinality;
- timezone boundary fixtures may be incomplete.

P1/P2 must be zero before Phase 3. P3 items require owners and release criteria.

## 18. Phase 1 recommendation

Start with a derive-only evaluator in pure modules and deterministic fixtures. It should return `effectiveState`, stage classifications, selected slots, artifact health, recovery eligibility, blockers, safe actions, and attention level. It must not write D1, create/claim/execute jobs, call upstream services, or alter public/admin behavior. Compare it with current V3 and recorded evidence before deciding on schema additions or shadow execution.

## 19. Scope and completion criteria

This deliverable is design only. It must not include feature-code changes, deploys, migrations, manual SQL, repair, scripts, Discord, job submission, admin operations, or scoring/ranking/publication execution. The design is ready for review when Phase 1 has an owner, fixtures, acceptance criteria, and a rollback decision.
